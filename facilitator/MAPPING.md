# Code-to-model correspondence

## Action map

| Code span / marker | Reference action | Model meaning |
|---|---|---|
| `client`: request `put_nowait` then wait | `Send(c)` | Append ID to FIFO and change client phase to waiting |
| `server`: `requests.get` and task creation | `Dispatch` | Remove head and enable that client's handler |
| `handle`: CHECK through entry to audit await | `Check(c)` | Test current stock and enter audit, or publish full |
| `Audit.record_attempt` suspension | Worker remains in `audit` | No stateful audit contents are relevant to allocation |
| `handle`: after audit through reply publication | `Commit(c)` | Allocate using stale eligibility, or recheck in fixed mode |
| `client`: reply `get` returns | `Receive(c)` | Consume mailbox, record result and finish |
| All clients have results | `Finish` | Explicit terminal self-loop |

The model is extracted from code plus the environment assumptions. It is not generated by a verified Python compiler. The code's text markers are stable references even if line numbers change.

## Atomicity rationale

Within this single asyncio event loop, ordinary synchronous code in these spans does not yield to another task. Audit introduces a real suspension boundary. Commit and `put_nowait` are one action because the code has no intervening await. Rejection during Check also publishes immediately. Adding a suspension to either span requires revisiting the model.

`requests.get` and reply `get` may complete immediately when data is already available. The model's split phases expose their logical effect, while allowing a broader abstract schedule than Python's particular ready-queue policy. The dispatcher also may drain several requests without yielding; modelling one dispatch per action conservatively allows more interleavings. We do not claim exact trace equivalence with that scheduler. The displayed failure has a real code-level witness, which addresses the relevant false-positive concern for this tutorial.

## State abstraction

- `remaining`: integer stock, allowed to become negative in the model's type domain so the safety error is observable.
- `booked`: set of successful client IDs, not a count alone. Capacity conservation and reply consistency remain expressible.
- `requests`: a sequence, preserving FIFO order.
- `clientPC`: ready, waiting, done.
- `workerPC`: idle, check, audit, done. The audit phase encodes the remembered successful guard; a separate Boolean `eligible` is unnecessary.
- `reply`: each client has empty, ok or full. A single slot suffices because each client issues one request and receives one reply.
- `result`: records consumed replies, so the observed result remains available after a mailbox empties.

Trace strings, audit payloads, wall-clock time, Python objects and server bookkeeping lists do not affect the chosen safety properties. Client IDs become model values such as c1 and c2. All these abstractions require review if the requirements change.

## Guards

Send requires ready. Dispatch requires a nonempty queue and an idle worker for its head. Check requires worker phase check and branches on remaining stock. Commit requires phase audit; in buggy mode it does not recheck stock. Receive requires a waiting client and a nonempty reply. Finish requires all clients done.

## Invariants and fairness

`Accounting` continues to hold even in the buggy model: a negative stock count can still balance the number of bookings. It is not a substitute for `NoOversell` or `StockNonnegative`. `ReplySound` checks identity consistency. `FullWhenExhausted` depends on the no-restock assumption. S6 follows from monotonically advancing one-shot client and worker phases; it is not a general idempotency proof.

Safety needs no fairness assumption. `FairSpec` adds weak fairness to dispatch and each per-client action. In particular, weak fairness of Commit represents eventual audit completion and scheduling. `AllReplied` is checked only in the optional liveness configuration. This assumption excludes permanent audit outages.

## Why the fix works here

After audit, the task reads remaining stock and conditionally decrements it without suspension. Every successful reservation therefore observes stock greater than zero at the same atomic step that consumes it. The initial check remains a fast rejection path. With one-shot clients, every successful decrement adds a distinct booking. These observations explain the repaired invariant; the finite TLC runs do not replace a general inductive proof.

The repair is specific to a single event loop and in-memory inventory. For multi-process database access, move the guard and update into an appropriate atomic database operation or transaction and model the relevant isolation semantics. Do not infer that an asyncio lock would coordinate independent processes.
